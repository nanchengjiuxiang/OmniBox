## 1. 方法学

- 设计稿仅读取 `<body>` 内文本；不执行 JavaScript、不加载 CSS、不做 OCR。

### 1.2 可见中文提取规则

1. 先删除 HTML 注释、`<script>...</script>`、`<style>...</style>`。
2. 删除 Material Symbols / Material Icons 图标字体元素，避免 `search`、`offline_pin` 等图标连字名混入文案。
3. 把 `div`、`p`、`li`、`h1`～`h6`、`header`、`button`、`label`、`td`、`br` 等块级标签替换为换行，其余标签替换为空格。这样相邻块不会粘成一条，而行内数字仍会保留在同一句里。
4. 对剩余文本执行 `html.unescape`，按 `\s+` 折叠为单个空格并去除首尾空白。
5. 只保留含 CJK 字符（`[\u4e00-\u9fff]`）的文本片段。
6. 过滤规则（脚本常量与注释中同样写明）：
   - 长度小于 2 的碎片不计；
   - 纯数字、纯符号、纯单位（如 `12`、`%`、`12 %`）不计；
   - 明显占位符（`Lorem`、`TODO`、`TBD`、`placeholder`、`占位符`、`待补充`、`示例文本`）不计；
   - 同一屏内完全相同的文案只计一次。
- 本次被占位符规则剔除：**0** 条。

说明：本脚本只统计 HTML 文本节点，**不统计** `placeholder`、`aria-label`、`title` 等属性中的中文，也不判断 CSS 是否把某个元素隐藏。因此「可见」是结构意义上的可见，不是渲染后的像素级可见。

### 1.3 匹配规则

对每条设计文案，依次尝试以下三级匹配；任一级命中即计为「已覆盖」：

1. **严格匹配**：设计文案（空白折叠后）是 Kotlin 源码原文（空白折叠后）的连续子串。
2. **宽松匹配**：两边都去掉数字、标点、空白、格式化占位符（`%d`、`%1$s`、`%.2f`、`${...}`）后，只保留汉字与拉丁字母并转小写，再做子串比较。这是需求指定的宽松口径，用于让 `"剩余 %d 天"` 命中设计稿「剩余 12 天」这类片段。
3. **纯中文兜底**：仅当设计文案的纯中文骨架不少于 4 个汉字，且该骨架出现在源码的纯中文骨架中时命中；用于处理 Kotlin 字符串模板或英文缩写夹在中间的长句。

宽松匹配只证明「字符序列在源码某处出现过」，不证明它属于同一控件、同一屏或同一语境；短词（如「设置」「打开」）尤其容易因全局搜索而命中。因此该指标衡量的是**文案存在性覆盖**，不是逐屏 UI 等价性证明。

### 1.4 为什么用文案覆盖替代像素比对

本机没有 Android 模拟器与系统镜像，无法逐屏启动应用并截图，因此无法做像素级 diff。设计包是 Google Stitch 导出的静态 HTML，界面文案以文本节点形式存在；Kotlin/Compose 实现的界面文案也以字符串字面量形式存在。在该约束下，中文文案覆盖率是一个**可离线、可复现、可审计**的代理指标：它能发现「整屏未实现」「关键标签漏写」「文案改写」等问题，但不能替代真实截图比对。

### 1.5 局限

- 文案存在不等于布局、层级、颜色、间距、交互正确；本报告不评价视觉还原度。
- 只读取 HTML 文本节点；`placeholder`、`aria-label`、`title` 等属性未计入，可能低估设计稿文案总量。
- 不执行 CSS；带 `hidden` / 响应式隐藏类的元素仍可能被抽取，可能轻微高估设计稿文案总量。
- 源码语料为 `.kt` 原文（含注释），注释中的相同文字也会被算作命中，可能轻微高估覆盖率。
- 长段落按整行比对，任何改写、增删标点之外的字词都可能造成未命中；短词则可能因全局出现而误命中。
- 覆盖率高低不代表功能完成度或代码质量；设计稿中纯图标、纯数值、动态单位等本就无可匹配中文的屏，覆盖率会天然偏低。
